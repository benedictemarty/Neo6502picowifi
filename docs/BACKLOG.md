# Backlog — Neo6502picowifi (firmware du modem Wi-Fi Pico W)

Stories reprises de Neo6502drive (`docs/BACKLOG.md`, épopée « périphérique réseau ») le 2026-09-18, à
l'extraction du firmware dans ce projet. Les stories 6502 (driver, terminal) restent dans Neo6502drive.
Contrainte transverse : `netsetup.neo`, `prophet.neo`, `pget.neo` et ProphetGui doivent continuer de
fonctionner sans modification.

Les gains de NeoNavigator sont de son côté : modem en USB plutôt qu'en UART, décodeur en assembleur (US17),
copie de rectangle (US16).

**Cœur 1** : utile surtout pour US-T3 (plusieurs handshakes TLS sans geler la liaison série) ; à précéder d'une
étude (pile réseau sur le cœur 1 : réactivité série pendant un handshake, tas avec 2 à 4 connexions TLS, écriture
flash avec l'autre cœur en pause, `malloc` partagé).

## Ajouts 2026-09-24 (anomalies relevées pendant la release 0.3.0)
| ID | P | User story | État |
|----|---|------------|------|
| US-W4 | P3 | En tant que PO, je veux que `ATI` n'annonce `last reset: watchdog` **que pour un vrai dépassement du watchdog**, afin de ne pas confondre un reflashage avec un blocage. Constat : après copie d'un UF2 (reboot du bootrom par le watchdog), `ATI` affiche `last reset: watchdog, stage 0`. Cause : `main.c` teste `watchdog_caused_reboot()` (vrai aussi pour le reboot du bootrom) et range son étape dans `scratch[4]`, registre que le SDK utilise pour distinguer un dépassement (`WATCHDOG_NON_REBOOT_MAGIC`, `hardware_watchdog/watchdog.c`) ; utiliser `watchdog_enable_caused_reboot()` et un autre registre pour l'étape. | **Terminé 2026-09-24** (0.3.1) — `src/reset_cause.[ch]` (testé sur PC) ; marqueurs dans `scratch[0..2]` ; sur carte : `AT+RST`, `AT+BOOTSEL (UF2 flash)`, `reboot (bootloader or debugger)` et `power-on` constatés ; dépassement réel du watchdog couvert par les tests PC seulement (pas de moyen de le provoquer sur carte) |
| US-W5 | P3 | En tant que PO, je veux des **compilations reproductibles** (même commit → même UF2), afin que l'empreinte publiée prouve quel binaire a été testé. Constat : deux compilations de `v0.3.0` ont donné des SHA-256 différents, à cause de `__DATE__ __TIME__` (`compile time:` de `AT+GMR`) ; piste : `SOURCE_DATE_EPOCH` = date du commit. Contournement appliqué pour 0.3.0 : c'est l'UF2 publié lui-même qui a été flashé et validé. | **Terminé 2026-09-24** (0.3.1) — `compile time:` = date du commit (UTC, `build_id.h`) ; deux compilations dans deux répertoires → UF2 identiques ; `tools/release.sh` le vérifie à chaque release |
